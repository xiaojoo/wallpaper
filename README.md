# SmartWallpaper — Windows 动态壁纸引擎 V0.1

按方案落地：`C++20 + Win32 + Direct3D 11 + DirectComposition + HLSL`，渲染引擎与设置 UI 分离。
渲染器 V0.1 已跑通并量过；Qt/QML 设置界面、GPU 粒子已做；视频、3D、后处理还没做
（见文末缺点与 `BACKLOG.md`）。

## 编译

```
cmake -S . -B bld -G "Visual Studio 17 2022" -A x64
cmake --build bld --config RelWithDebInfo
```

产物 `bld/bin/RelWithDebInfo/WallpaperRenderer.exe`，`Wallpapers/` 与 `Shaders/` 每次构建自动
拷到 exe 旁边（`stage` 目标，改 .hlsl 不用重编 C++）。

## 运行与控制

```
WallpaperRenderer.exe                          双击/命令行直接开跑，读同目录 config.json
WallpaperRenderer.exe --selftest 20            跑 20 秒自动退出并把测量结果写日志
WallpaperRenderer.exe --wallpaper embers       指定壁纸
WallpaperRenderer.exe --window                 普通顶层窗口，不碰桌面（开发用）
WallpaperRenderer.exe --no-power               忽略遮挡/全屏降帧（开发用，量帧率时才用）

WallpaperRenderer.exe --ctl status             读运行中实例的真实状态（JSON）
WallpaperRenderer.exe --ctl apply aurora M0    换壁纸（M0/M1/all）
WallpaperRenderer.exe --ctl pause | resume | reload | quit
WallpaperRenderer.exe --ctl quality battery
WallpaperRenderer.exe --ctl fps 30
WallpaperRenderer.exe --ctl fps 30 M0            只给这一块屏设上限
WallpaperRenderer.exe --ctl rotate on | off | interval 30
WallpaperRenderer.exe --ctl autostart on | off   登录自启（HKCU Run 单值）
WallpaperRenderer.exe --ctl addimage "D:\pics\a.jpg"   把一张图片变成壁纸包
```

控制通道是命名管道 `\\.\pipe\SmartWallpaper.Renderer`，一行一个 JSON。以后 Qt 设置界面走同一条管道，
不需要改渲染器。托盘图标也有同一套菜单（壁纸 / 显示器 / 质量 / 最大帧率 / 暂停 / 重载 / 退出）。

日志：`logs/renderer-<pid>.log`；配置：exe 同目录 `config.json`（首次运行自动写出）。

## 设置界面（Qt 6.11 + QML）

```
cmake -S . -B bld -G "Visual Studio 17 2022" -A x64 -DCMAKE_PREFIX_PATH=D:/Program/Qt/6.11.2/msvc2022_64
cmake --build bld --config RelWithDebInfo
bash tools/run-ui.sh                  # 暂存 qml/ 并启动（改 QML 不用重编）
bash tools/run-ui.sh --with-renderer  # 顺便把渲染器起来
SmartWallpaper.exe --select embers    # 直接选中一张，让轮播停在它上面
SmartWallpaper.exe --settings         # 直接打开设置对话框
SmartWallpaper.exe --settings-tab monitors   # 打开并停在某一类（general/monitors/power/wallpapers/renderer）
```

数和上一帧不同的采样点），`GetWindowRect` 数不出动画：

和桌面同一个 `nowSeconds` 时间轴、自己 30 fps 预算，1280x720），像素走命名共享内存
（`Local\SmartWallpaper.Preview`，seqlock 保护）给设置窗里的 `LivePreview` 图元；轮播小卡片和字幕条
照旧浮在它上面。所以大图里就是**正在下的雪**，没有"一段放完弹回开头"这件事。
实测：生产 **30.0~30.6 帧/秒**、端到端延迟 **0~15 ms**、`dropped=0`；连拍 72 帧大图亮度 72.8~85.3、
**空白帧 0 张**（空白卡片是 8.2）。
（更早记的 21.6 帧/秒是下面那条心跳故障摊出来的平均值——每 3 秒停一次，不是稳态速率。）
两条踩过的坑：**别用 `Image` 每帧换 URL** —— 那样 Qt 每帧新建一张纹理并在加载期间把图元清空，
实测只有 16~18 帧/秒且整块大图一闪一闪；`LivePreview` 是自绘图元，同一块底图反复重绘，才既不断流也不闪。
**`preview.fps` 这个字段以前会说谎**（pacer 自己在 15 和 30 之间跳），现在按 `drew` 计数每秒算一次。
三条护栏：设置窗每 ~700 ms 一次 `previewbeat`，**3 秒没心跳渲染器自停**（窗口崩了不会留一路常驻 GPU）；
这条心跳以前**按 tick 计数**，而 `root.current` 是每秒 status 刷新时重绑的 JS 对象，每次重绑都会把计数
清零，于是心跳从来没发出去过——第二路每切换一次只活 3 秒就退回帧条，帧条又从头开始放，这正是"切换有
一小段卡顿"和"重头开始"两处报障的同一个根因；现在按墙钟发，实测每秒 1.4 次、第二路连续 30 帧/秒不掉。
**这条 3 秒护栏是这么量的**：开一扇设置窗（第二路 30.07 帧/秒）→ `taskkill /F` 强杀（QML 的
`onVisibleChanged` 根本不会跑）→ 每秒采一次 `status`：`preview.on` 到 **t=3 s 变 false**、fps 归零；
同一时刻桌面那路全程 9.68–10.56 帧/秒（有窗口压屏所以被降到 background 档）、`corner_samples_changed`
每秒都在涨（1545→1552）→ **强杀一扇设置窗的代价最多 3 秒的多余 GPU 活，桌面不受影响**。
`build/tmp/watch-preview.ps1` 就是这个采法。
设置窗收不到新帧就 `running=false`，大图**自动退回下面那条帧条**（杀掉渲染器实测：帧条像素差 0 → 1.65，
之前是整块冻住——因为渲染器不在时 `refresh()` 每秒要阻塞 800 ms 的管道超时，42 ms 的播放时钟被饿到
~2 次/秒；现在离线时把超时收到 150 ms 并把轮询退到 2 秒一次）；预览实例按
壁纸 id 缓存 12 个，不然每换一张都要在帧循环里重编译 HLSL（实测会卡出 1 秒的空窗）。
**切换那一下不再停**：共享段的头里带"这帧是哪张"（`idHash`），点下箭头到段里出现新壁纸的第一帧实测
**11~54 ms**（冷 Prepare 的那一次也落在这里面），这段时间大图继续播**上一张**的实时帧而不是切去静帧——
静帧和实时帧是动画里不同的瞬间，换过去就是一次可见的跳动；超过 120 ms 还没等到才回落静帧。
分辨率角标是真数据：导入的图片显示 WIC 解出的原始像素，
着色器壁纸没有固有分辨率，显示"着色器生成"，不编数字；粒子壁纸在这旁边多一枚 `GPU 粒子: N`，
取的是包里真实的 `particles.count`（截图 `build/shots/ui_carousel.png` 的 Snowfall）。

界面不持有状态：每秒从 `status`/`list` 读，所有改动走同一条命名管道由渲染器落盘。中文默认，
两套文案在 `Bridge.cpp` 一张表里，缺条目直接显示键名。控件全自绘。

## 壁纸包格式

```
Wallpapers/aurora/
    wallpaper.json      名称、fps、quality、shader、params、textures
    main.hlsl           运行期用 d3dcompiler_47.dll 编译，不重编程序
    textures/*.png      WIC 解码成 BGRA 纹理，按数组顺序绑到 t0..tN
```

`wallpaper.json` 的 `params` 通过 **着色器反射**按名字绑进 `cbuffer Params : register(b1)`，
支持 float / int / bool / float2 / float3 / float4 / 标量数组；JSON 里有、着色器里没声明的键会在
日志里点名（`params.xxx is in wallpaper.json but not in the shader`）。

引擎契约在 `Shaders/Fullscreen.hlsl`：一个覆盖全屏的三角形（`SV_VertexID`，无顶点缓冲），
`uTime / uRes / uMouse / uScene / uPerf` 五个 `float4`，外加 hash / 值噪声 / fbm / 色调映射 / sRGB。
共享头用 `#ifndef` 包含保护而不是 `#pragma once`：引擎的 `ID3DInclude` 每次 `Open()` 都交给编译器
一块新内存，`#pragma once` 会把同一个文件当成好几个文件，于是 `uTime` 重复定义。

## GPU 粒子壁纸

`Wallpapers/snowfall` 是第一条粒子通路：状态全在 GPU 上，CPU 每帧只上传时间和参数，不写任何粒子。

```
wallpaper.json
    "renderer": "particles",
    "entries":  { "cs": "CSMain", "pvs": "ParticleVS", "bg": "PSBackground" },
    "particles": { "count": 6000 },
    "params":   { "fall_speed": 0.075, ... , "octaves": 4 }
main.hlsl     CSMain 积分 / PSBackground 夜空 / ParticleVS 每粒子 6 顶点 / PSMain 软圆盘
```

一帧三步：compute 写 `u0` 的结构化缓冲 → 一个全屏三角形画背景 → `count*6` 个顶点叠加画粒子。
契约由引擎把住，写错的包在加载时就被拒：

- 粒子布局 48 字节（`Shaders/ParticleCommon.hlsl` 的 `struct Particle` ↔ `ParticleSystem::Stride`）。
- `CSMain` 必须是 `[numthreads(64,1,1)]`，引擎按 64 除算 group 数（`ParticleSystem::Threads`）。
- `Params` 里必须有 `int count`，引擎用缓冲真实长度覆盖它，着色器永远不可能和缓冲不一致。
- `fxc` 只在 `cs_5_0` 里声明 `RWStructuredBuffer`，所以写视图和 `CSMain` 都要包在
  `#ifdef SW_COMPUTE` 里（这个宏由引擎在编译 compute 入口时定义）。
- 粒子缓冲占 `t0`，包自带的纹理顺移到 `t1..`，所以一张粒子壁纸最多 7 张贴图。

`--ctl status` 里每张粒子壁纸带 `particles` / `particle_moved_samples` / `particle_out_of_bounds` /
`particle_positions_hash`：把结构化缓冲回读到 CPU 再哈希，是"仿真真的在动"的直接证据，
和像素角点回读互相独立（角点可以一动不动而粒子仍在跑）。

## 已知缺点（没做的别当做了）

1. **hover 这一类没法自动验**：自绘 Qt 控件 UIA 枚举不到，`PostMessage WM_MOUSEMOVE` 驱动不了 Qt 的
   hover，他人在机器前时光标几百毫秒会漂 13–30px —— 划过去亮不亮要人眼过一遍。
   **点击链路已经走通并量过**：`SetCursorPos` + `mouse_event`，按下之前先 `WindowFromPoint`
   确认落点属于被测窗（不确认那一次点到了别人的窗口）。量的对象是滑块的开与关、两个下拉的展开与选中、
   设置弹框的叉 / 卡片内空白 / 卡片外遮罩，每条都是点下去之后从渲染进程的控制管道读回状态。
   `tools/guarded-click.ps1 -Post` 是同一件事的**不占光标**版本：直接 `PostMessage` 三个鼠标消息给窗口
   自己的队列。桌面被 topmost 的游戏客户端盖住时只有这条路能走（`HWND_TOPMOST` 也压不住它，
   `WindowFromPoint` 会连着两次拒绝发点击 —— 拒得对，那一下会落进他的游戏里）。
2. **视频壁纸没做**（Media Foundation 通路未写）。图像壁纸已做：`addimage` 建壁纸包 +
   `Shaders/Image.hlsl` 覆盖裁切 + 缓慢 Ken Burns；**导入项已可删除**（设置 → 壁纸 的预览卡角标，
   两下确认，正在用作壁纸的那张会被拒绝），**重命名仍未做**。
   覆盖裁切这条**原来是反的**（注释写着 cover，代码把 UV 窗口 `除以` 裁切系数 → 窗口被撑到纹理之外，
   采样器是 wrap，于是非 16:9 的图在屏幕上只占中间一条、上下是照片对边重复出来的画面）。
   拿一张 1000x1000 的夹具量过：改前 480x270 缩略图里照片只占中间约 56% 高、上下两条是回绕重复；
   改成 `乘以` 之后整幅铺满（同一夹具逐通道平均变化 41.87）。**对照：他自己那张 1920x1080（宽高比正好
   等于屏幕）改前改后逐像素相同**，所以这次修正不影响已经正常的图。夹具已删除，目录回到 4 项。
   **`Json::Of("字面量")` 会选中 `Of(bool)`**（指针→bool 是标准转换，压过到 `std::string` 的用户定义
   转换），所以导入器写出来的清单是 `"renderer": true`、`"quality": true`，`config.json` 的 `_comment`
   是 `true`，托盘"设为壁纸"发出的命令体是 `{"cmd":true}` —— 渲染器 `strOr("cmd")` 读成空串，整条命令
   被丢掉，而托盘照样弹"Wallpaper applied"。已加 `Of(const char*)` 重载从根上堵掉这一类，实测新导入的
   清单是 `"renderer": "d3d11"`、`_comment` 是字符串。**残留：改之前导入的那几张（`local_01`）清单里
   仍然是 `true`**，读清单时 `strOr` 拿默认值，行为不变，只有重新导入才会写对。托盘那条这台机
   `tray: false`，没实测过。
3. **粒子已做**（GPU compute，见"GPU 粒子壁纸"一节）；**3D / 后处理没做**。粒子的质量档还没接：
   `particles.count` 现在是包里的固定值，不随 battery/low 档缩水。另外那路"仿真在动"的回读是
   每秒把整块结构化缓冲拷回 CPU（25 万粒 = 12 MB），量具有代价，正式版应当只在一开始几秒开。
4. **多显示器只实现未实测**：这台机器只有一块屏。每显示器一路窗口 + 各自帧率预算 + 各自遮挡判定
   的代码在，第二路的真实行为没验证过。
5. **质量档目前是半件东西**：只影响着色器看到的 `uScene.x`/`uPerf.y` 和低档的帧率上限，
   没有引擎级降分辨率渲染（要加一次离屏 RT + blit pass）。
6. **锁屏 / 关屏降帧未实测**：三个电源通知都注册成功（日志 `watching GUID_...`），
   `WTSRegisterSessionNotification` 也成功，但没真锁一次屏去验 0 FPS 生效。
7. 结束进程后 explorer 留下的那个壁纸 `WorkerW` 不会自动消失（重启 explorer 才回到原始结构）。
   实测它不影响图标点击与系统壁纸，但那是别人建的结构，退出时我没去拆它。
8. **预览的"尺寸"已经和桌面对齐，"质感"还差一档**：帧条现在按大图在屏幕上的宽度（1280x720）渲，
   雪片占画面的比例和桌面一致（`uPerf.z`）。但着色器的雪片是"实心核 + 高斯光晕 + 叠加混合"，
   缩到 1/3 之后光晕掉进亚像素，实测同一尺度下预览的亮斑等效半径 1.69 px、桌面 5.08 px ——
   看着比桌面细、比桌面暗。要完全一样只能**按屏幕分辨率渲再 GPU 降采样**（mip + 一次 blit），
   那一路还没做。同尺度下 JPEG(q85) 和 PNG 的差只有 4%（1535 vs 1599 个亮斑），编码不是原因。
9. **带状态的着色器（snowfall 的 compute 积分）预览节奏**：帧条靠每次抓取传对的 `delta` 才落在真实
   的一秒上；`Thumbnailer::Grab` 以前恒传 `1/60`，所以那 24 张其实只覆盖 0.4 秒的雪，播出来是慢动作。
   现在按 `frameSpan_/frameCount_` 传，改帧数时这个数要一起看。

## 这台机器上量出来的几条坑（换机器要重验）

- `FindWindowW(L"Progman", NULL)` 返回 0，但 `EnumWindows` 按类名能找到、`GetShellWindow()` 也能拿到。
  所以代码里用 `GetShellWindow()` + 类名校验 + `EnumWindows` 兜底，不靠 `FindWindow`。
- 向 Progman 发 `0x052C` **确实**建出了壁纸 `WorkerW`，但它是 **Progman 的子窗口**，不是方案假设的
  顶层兄弟窗口。所以"找 DefView 宿主之后的那个顶层 WorkerW"这条经典路径在这台机上什么也找不到；
  而"挂到 Progman 子列表最底部"的退路会把我们埋在那个 WorkerW 下面——它画着系统壁纸，于是屏幕上一帧
  都看不到我们的画面，而日志里 60 FPS 一切正常。正确做法是在 Progman 子链里把自己插到
  `SHELLDLL_DefView` **正下方**：`SetWindowPos(hwnd, defView, ...)`。日志 `host=` 会写明走了哪条路径。
- **省电把渲染停掉之后，屏幕上留着的是上一帧**：`state=fullscreen` / `cap_fps=0` / 槽 `frames=0` 时
  抓屏照样能抓到一张完整的壁纸，改任何东西它都不动 —— 看起来就是"这个设置没生效"。量桌面之前先读
  `status` 里那颗 `measured_fps`，是 0 就别量（前台被一个 3840x2160 的游戏客户端盖住时就是这个样子）。
- 判"壁纸没显示"不能只看截图：进程内角点回读显示像素在动、全屏截图却纹丝不动，这种组合只可能是
  层级/遮挡问题，不是渲染问题。反过来，桌面被全屏应用盖住时截图是假阴性，要挑桌面可见的时刻量。
- **量 Qt Quick 窗口的动画节拍，`PrintWindow` 和 `QT_QPA_PLATFORM=offscreen` 都会假死**：被别的窗口
  盖住时 PrintWindow 只给最后一张过期位图（实测 6 秒 251 张、逐张差 0.000），离屏平台则事件循环照跑
  （Timer 507 次、图片 24 张全部 Ready）但 scene graph 不推进 —— `FrameAnimation.running=true` 而
  `triggered` 一次不发。所以动态预览的时钟用的是贴着墙钟重新对时的 `Timer`，节拍从 `ui.log` 里读，
  不依赖屏幕可见。`tools/cadence-screen.ps1` 是抓真实屏幕的那把尺子（前提：窗口没被盖住）。
- **我们的窗口是 Progman 的子窗口，所以桌面一有操作就会同步等我们**：右键菜单和 F5 刷新会向 Progman
  子链里每个窗口发消息，而跨线程的 `SendMessage` 只有 `GetMessage`/`PeekMessage` 才会派发，
  `MsgWaitForMultipleObjects` **不为它醒来**（`QS_SENDMESSAGE` 不支持）。所以按帧间隔睡觉 = 让
  桌面等我们：10 FPS 时实测我们的窗口回一条 `WM_NULL` 要 **85~98 ms**，同一时刻 Progman /
  `SHELLDLL_DefView` / `SysListView32` 都是 0~1 ms；暂停态那条路原本是裸 `Sleep(200)`，更久。
  修法是把等待切成 16 ms 一片（`FPSController::MessageQuantumMs`），每片醒来回到循环顶排水，
  降到 **1.1~16.3 ms**；代价是 `loop: 11 iters/s → 71 iters/s`，而 `drew`、帧时、CPU 全部没变
  （10.00 FPS / 100.00 ms / 1.4 %）。量具：`tools/probe-desktop-latency.ps1`（四个窗口的往返时延，
  `-ClickAtSample n` 还能把桌面右键菜单也一起复现出来）。
